# LLM Council Transcript — Great Guest Автономность
**Дата:** 21 июня 2026  
**Проект:** Great Guest  
**Методология:** Karpathy LLM Council (5 советников → анонимное рецензирование → синтез председателя)

---

## Исходный вопрос

Что ОДНО нужно построить/починить первым чтобы Great Guest работал без участия Сергея?  
Варианты: (A) Платёжная интеграция ЮKасса, (B) Self-service онбординг в боте, (C) Критические баги безопасности, (D) GitHub→Vercel auto-deploy.

## Контекст

- **Продукт:** QR-лояльность через Telegram для ресторанов
- **MVP:** Telegram-бот + мини-апп + панель владельца + Vercel/Supabase backend
- **Основатель:** Сергей Шпак, MBA, 17 лет HoReCa (Pernod Ricard), соло, не технарь
- **Стек:** Node.js serverless (Vercel) + Supabase PostgreSQL + Telegram Bot API + Telegram Mini App
- **Статус:** MVP работает, первые продажи начинаются

---

## Шаг 1 — Ответы советников

### The Contrarian

Все четыре варианта неправильные, потому что вопрос поставлен неправильно. Три-пять клиентов не дадут достаточно сигнала, чтобы знать, что именно автоматизировать. Но если принять условия вопроса — ответ очевиден: C, безопасность.

A (ЮKасса) — бессмысленно без клиентов. B (Онбординг) — до него не дойдут, если данные утекут. D (auto-deploy) — это не блокирует продажи. C — не опция, это обязательное условие существования. Открытый RLS означает, что любой школьник с Postman может записать что угодно в базу. В HoReCa сарафанное радио работает в обе стороны. Реальный вопрос: есть ли у Сергея технический партнёр, который закроет C за неделю?

---

### The First Principles Thinker

Сергей задаёт неправильный вопрос. Любые инвестиции в автоматизацию — это автоматизация гипотезы, а не бизнеса. Но вопрос о безопасности — другое. Это не автоматизация. Это фундамент.

Открытый RLS означает, что данные одного ресторана видны другому. Если первый клиент подключится к системе с этими дырами — это готовая катастрофа. Ресторатор покажет систему конкуренту. Один такой случай = потеря клиента + репутации в узком HoReCa-сообществе, где все знают всех. Настоящий ответ: C, и только C. Не потому что безопасность важнее роста. А потому что без C нельзя безопасно подключать первых клиентов.

---

### The Expansionist

База гостей — это и есть настоящий бизнес. Никто не говорит вслух: Great Guest сидит на данных о поведении гостей тысяч ресторанов. Но сначала — A, платёжная интеграция. Платёж = момент истины для unit economics. Когда ресторан платит без Сергея — у него появляется реальная LTV, реальный CAC, реальный churn.

Скрытый апсайд: ЮKасса даёт не только транзакции — она даёт доверие юридического лица. Self-service онбординг нужен через 30 дней — личный онбординг сейчас = конкурентное преимущество, не слабость. Плати → данные → платформа.

---

### The Outsider

Вопрос поставлен неправильно. «Система работает без участия» — это не про платежи и не про онбординг. Это про то, что система вообще работает.

Пункт D стоит последним, но это единственное, что реально ломает всё остальное. Если auto-deploy сломан, то когда Сергей починит баг безопасности или добавит онбординг — изменения не попадут в прод. Первый клиент придёт, система упадёт, Сергей выкатит фикс в 23:00, что-то сломает. Ответ: сначала D, потом C, потом B, потом A. Платежи — последними.

---

### The Executor

C → D → B. В этом порядке.

Понедельник утром, первые 6 часов: чинишь баги безопасности. auth_date validation — 1 час. Atomic counter — 1.5 часа. RLS политики — 2 часа. Тест — 1 час. Вторник утром — D auto-deploy: 1–2 часа, GitHub Secrets в Vercel. Среда-четверг — B онбординг. A ЮKасса — после первых 3 клиентов. Сначала закрой их вручную, выставь счёт. Автоматизировать оплату до продаж — строить кассу в пустом магазине.

## Шаг 3 — Взаимное рецензирование

### Рецензент 1
- **Сильнейший:** E (First Principles) — конкретный механизм провала в HoReCa контексте
- **Главное слепое пятно:** A (Expansionist) — ЮKасса в РФ = 2–4 недели регистрации, соло нетехнарь не реализует
- **Что пропустили все:** нужна диагностика реального кода, а не абстрактное ранжирование

### Рецензент 2
- **Сильнейший:** D (Executor) — единственный с временными оценками, actionable для нетехнаря
- **Главное слепое пятно:** A (Expansionist) — ЮKасса поверх дырявой базы = юридический риск
- **Что пропустили все:** нанять/найти технического партнёра на 8–10 часов — это и есть первый шаг

### Рецензент 3
- **Сильнейший:** D (Executor) — конкретные шаги с временем
- **Главное слепое пятно:** C (Outsider) — «auto-deploy важнее безопасности» — перфекционизм, не стартап
- **Что пропустили все:** может онбординг — 10-минутный Telegram-скрипт, не автоматизация

### Рецензент 4
- **Сильнейший:** D (Executor) — рабочий план, а не мнение
- **Главное слепое пятно:** A (Expansionist) — не ответил на вопрос, уклонение
- **Что пропустили все:** есть ли живые клиенты? Если нет — правильный ответ B (онбординг)

### Рецензент 5
- **Сильнейший:** B (Contrarian) — чёткий аргумент: без RLS нельзя подключить ни одного клиента
- **Главное слепое пятно:** A (Expansionist) — «первый рубль» поверх открытого RLS = первый иск
- **Что пропустили все:** работает ли бот прямо сейчас? Что останавливает первую продажу завтра?

## Шаг 4 — Синтез председателя

### Где совет согласен

**C (безопасность) — блокер, не опция.** Четыре из пяти советников и все пять рецензентов сошлись независимо. Открытый RLS = данные ресторана A видны ресторану B. В HoReCa один такой инцидент = конец репутации до масштабирования. Нельзя брать деньги через продукт с открытой базой.

**A (ЮKасса) — последняя.** Единогласно. Регистрация 2–4 недели, юридическая ответственность при утечке, первые клиенты закрываются вручную.

**Сергей не технарь — нужен человек с руками.** Все рецензенты зафиксировали: без технического исполнителя все решения совета — теория.

### Где совет расходится

**C против D — что первее?** Outsider: без auto-deploy исправленная C не попадёт в прод. Executor и First Principles: C первее, деплой поверх дырявой базы только ускоряет катастрофу. Разрешение: D занимает 1–2 часа и не конфликтует с C — это порядок в рамках одного дня, не реальный выбор.

**B онбординг:** автоматизировать или задокументировать? Рецензент 3 поднял правильный вопрос: может, это 10-минутный Telegram-скрипт, а не система.

### Слепые пятна

1. Никто не спросил: есть ли живые клиенты прямо сейчас?
2. Техпартнёр/фрилансер не обсуждался как первый шаг — а это реальный первый шаг для нетехнаря
3. Диагностика кода перед ранжированием — совет не знал точный масштаб проблем

### Рекомендация

**C, начиная сегодня, через найм технического исполнителя на 8–10 часов.** Порядок: RLS политики → auth_date validation → atomic counter → тест → D (auto-deploy). Всё за один рабочий день при правильном человеке. Затем B как задокументированный скрипт. A после первых 3 клиентов.

### Одно действие прямо сейчас

Написать в Telegram: «Ищу Node.js/Supabase разработчика на 8–10 часов, задача — закрыть критические дыры безопасности (RLS + auth), оплата сегодня» — и отправить в три чата: локальный dev-чат, Upwork, или к знакомому технарю из сети.

## Приложение: Аудит безопасности (security-reviewer agent)

### КРИТИЧНО

1. **УДАЛИТЬ api/run-migration.js** — публичный POST, запускающий произвольный DDL без аутентификации. RCE для БД.
2. **restaurant-dashboard.js:160–166 globalGuests** — все гости системы видны любому владельцу. 152-ФЗ.
3. **webapp-init.js** — нет проверки auth_date. Бесконечное replay-окно.
4. **guest-preview.js** — нет аутентификации, ПДн открыты по токену.
5. **owner_subscriptions** — нет RLS миграции.
6. **send-offer.js** — не проверяет принадлежность гостя владельцу.

### ВАЖНО

7. In-memory rate limiting (Map) в send-offer.js/bonus-visit.js — теряется на Vercel cold starts.
8. confirm-visit.js — non-atomic visit_count (SELECT→compute→UPDATE).
9. CORS `*` на всех /api/ маршрутах.

---

## Приложение: QA-ревью (qa-reviewer agent)

### КРИТИЧНО

1. **Таблица owner_subscriptions не существует** — 100% runtime crash при любом действии владельца.
2. **Race condition на QR** — двойное сканирование с двух телефонов одновременно возможно.
3. **Нет проверки подписки в runtime** — владелец с истёкшей подпиской работает до перезагрузки.
4. **guest-preview.js без auth** — ПДн без контроля доступа.

### ВАЖНО

5. IDOR в confirm-visit.js — нет проверки ownership ресторана.
6. Telegram API failures не логируются — визит засчитан, гость не уведомлён.
7. Нет индекса на offers(restaurant_id, created_at DESC).
8. Нет rate limiting на create-qr.js.
