Что построить первым для автономной работы системы?

Сергей (соло, не технарь, HoReCa-эксперт) начинает первые продажи Great Guest. MVP работает. Что ОДНО нужно сделать первым, чтобы система могла работать без его участия?

Варианты: (A) Платёжная интеграция ЮKасса · (B) Self-service онбординг в боте · (C) Критические баги безопасности · (D) GitHub→Vercel auto-deploy
5 советников · 5 рецензентов · Синтез председателя · + Аудит безопасности + QA-ревью

Вердикт совета

Где совет согласен

  • C (безопасность) — блокер, не опция. Четыре из пяти советников и все пять рецензентов сошлись на этом независимо. Открытый RLS = данные ресторана A видны ресторану B. В HoReCa один такой инцидент — конец репутации до масштабирования.
  • A (ЮKасса) — последняя. Единогласно. Регистрация 2–4 недели, юридическая ответственность при утечке, первые клиенты закрываются вручную.
  • Сергей не технарь — нужен человек с руками. Все рецензенты зафиксировали: без технического исполнителя все решения совета — теория.

Где совет расходится

C против D — что первее? Outsider говорит: без auto-deploy исправленная безопасность не попадёт в прод. Executor и First Principles говорят: C первее, потому что деплой поверх дырявой базы только ускоряет катастрофу. Разногласие разрешимо — D занимает 1–2 часа и не конфликтует с C: это порядок в рамках одного рабочего дня.

Слепые пятна, которые поймал совет

  • Никто не спросил: есть ли живые клиенты прямо сейчас? Если есть — безопасность горит немедленно.
  • Техпартнёр/фрилансер не обсуждался как первый шаг. Для нетехнаря первое действие — не "открой GitHub", а "найди человека, который откроет GitHub".
  • B (онбординг) может быть просто задокументированным 10-минутным Telegram-скриптом, а не автоматизацией.

Рекомендация

C, начиная сегодня, через найм технического исполнителя на 8–10 часов. Порядок работ: RLS политики → auth_date validation → atomic counter → тест → D (auto-deploy). Всё закрывается за один рабочий день при наличии правильного человека. После — B онбординг как задокументированный скрипт. A ЮKасса — после первых 3 клиентов.

Одно действие прямо сейчас

Написать в Telegram: «Ищу Node.js/Supabase разработчика на 8–10 часов, задача — закрыть критические дыры безопасности (RLS + auth), оплата сегодня» — и отправить в три чата: локальный dev-чат, Upwork или к знакомому технарю из сети. Без технического исполнителя все остальные решения совета — теория.

Что нужно исправить (по приоритету)

1

УДАЛИТЬ api/run-migration.js

Публичный POST-эндпоинт без аутентификации, запускающий произвольный DDL от имени суперпользователя на продакшн базе. Remote code execution эквивалент для БД.
2

СОЗДАТЬ таблицу owner_subscriptions (миграция 005)

Таблица используется в 5 API-файлах, но не существует ни в одной миграции. 100% runtime crash при любом действии владельца ресторана.
3

restaurant-dashboard.js: globalGuests — скоупить к своим гостям

Строки 160–166 возвращают TOP 200 гостей ВСЕЙ системы любому авторизованному владельцу. Нарушение 152-ФЗ. Любой владелец может писать гостям конкурентов.
4

guest-preview.js: добавить аутентификацию

Любой человек с токеном QR получает first_name, last_name, username, visit_count гостя без каких-либо прав. Токены утекают через api.qrserver.com referrer logs.
5

webapp-init.js: добавить проверку auth_date (3600 секунд)

Единственный endpoint без проверки auth_date. Бесконечное окно replay-атаки — старый initData работает вечно.
6

owner_subscriptions: добавить RLS политики

Единственная таблица без RLS-миграции. После создания таблицы (пункт 2) нужно немедленно добавить политику service_role_all.
7

create-qr.js: добавить rate limiting

Нет ограничений на генерацию QR. Каждый QR — запись в pending_visits. DoS через миллионы QR за час возможен без ограничений.
8

Починить GitHub → Vercel auto-deploy

Сейчас требует ручного npx vercel --prod. Без этого каждый деплой = риск. Настройка: Vercel GitHub integration + Secrets за 1–2 часа.
9

send-offer.js: проверить принадлежность гостя владельцу

Владелец может рассылать офферы гостям чужих заведений (через globalGuests утечку). После фикса пункта 3 — закрывается частично.
10

confirm-visit.js: перейти на атомарный INCREMENT через RPC

visit_count обновляется через SELECT+UPDATE. Атомарный claim pending_visits (строки 21-27) защищён, но счётчик гостя нет. Фикс: supabase.rpc('increment_visits', ...).
Ответы советников
Contrarian «Вопрос неправильный — но ответ очевиден: C»
Все четыре варианта неправильные, потому что вопрос поставлен неправильно. Три-пять клиентов не дадут достаточно сигнала, чтобы знать, что именно автоматизировать. Но если принять условия вопроса — ответ очевиден: C, безопасность.

A (ЮKасса) — бессмысленно без клиентов. B (Онбординг) — до него не дойдут, если данные утекут. D (auto-deploy) — это не блокирует продажи. C — не опция, это обязательное условие существования.

Открытый RLS означает, что любой школьник с Postman может записать что угодно в базу. В HoReCa сарафанное радио работает в обе стороны. Реальный вопрос: есть ли у Сергея технический партнёр, который закроет C за неделю?
First Principles «C — фундамент, не автоматизация»
Сергей задаёт неправильный вопрос. Любые инвестиции в автоматизацию — это автоматизация гипотезы, а не бизнеса. Но вопрос о безопасности — другое. Это не автоматизация. Это фундамент.

Открытый RLS означает, что данные одного ресторана видны другому. Если первый клиент подключится к системе с этими дырами — это готовая катастрофа. Ресторатор покажет систему конкуренту. Один такой случай = потеря клиента + репутации в узком HoReCa-сообществе, где все знают всех.

Настоящий ответ: C, и только C. Не потому что безопасность важнее роста. А потому что без C нельзя безопасно подключать первых клиентов.
Expansionist «A первым — база данных гостей это настоящий бизнес»
База гостей — это и есть настоящий бизнес. Никто не говорит вслух: Great Guest сидит на данных о поведении гостей тысяч ресторанов. Но сначала — A, платёжная интеграция.

Платёж = момент истины для unit economics. Когда ресторан платит без Сергея — у него появляется реальная LTV, реальный CAC, реальный churn. Без этого он продаёт «намерения», а не бизнес.

Скрытый апсайд: ЮKassa даёт не только транзакции — она даёт доверие юридического лица. Ресторан, который заплатил, становится контрактным партнёром. Self-service онбординг нужен через 30 дней — личный онбординг сейчас = конкурентное преимущество, не слабость. Плати → данные → платформа.
Outsider «D важнее всего — без него всё остальное рискованно»
Вопрос поставлен неправильно. «Система работает без его участия» — это не про платежи и не про онбординг. Это про то, что система вообще работает.

Пункт D стоит последним, но это единственное, что реально ломает всё остальное. Если auto-deploy сломан, то когда Сергей починит баг безопасности или добавит онбординг — изменения не попадут в прод. Первый клиент придёт, система упадёт, Сергей выкатит фикс в 23:00, что-то сломает.

Ответ: сначала D, потом C, потом B, потом A. Платежи — последними. Первые 3–5 клиентов закрываются вручную.
Executor «C → D → B. Конкретный план с часами»
C → D → B. В этом порядке.

Понедельник утром, первые 6 часов: чинишь баги безопасности. auth_date validation — 1 час. Atomic counter — 1.5 часа. RLS политики — 2 часа. Тест — 1 час.

Вторник утром — D auto-deploy: 1–2 часа, GitHub Secrets в Vercel.

Среда-четверг — B онбординг.

A ЮKасса — после первых 3 клиентов. Сначала закрой их вручную, выставь счёт. Автоматизировать оплату до продаж — строить кассу в пустом магазине. Открой GitHub прямо сейчас и начни с RLS.
Взаимное рецензирование
Рецензент 1 — Сильнейший: E (First Principles), Слепое пятно: A (Expansionist)
Сильнейший — E. Самый чистый аргумент: C — не опция автоматизации, а условие безопасного подключения первых клиентов. Конкретный механизм провала (ресторатор показывает систему конкуренту → RLS → данные видны) точно попадает в HoReCa-контекст, где репутация разрушается за один разговор.

Наибольший слепой угол — A. A убеждает, что платёж = unit economics и доверие. Но пропускает очевидное: ЮKасса в РФ = 2–4 недели только на регистрацию. Сергей соло, не технарь. Это не «построить первым» — это строить последним среди зависимостей.

Что пропустили все: нужна диагностика реального состояния кода, не абстрактное ранжирование. Совет должен был начать с диагностики.
Рецензент 2 — Сильнейший: D (Executor), Слепое пятно: A (Expansionist)
Сильнейший — D. Единственный, кто дал конкретные временные оценки и чёткую последовательность. Actionable для нетехнаря, нанимающего разработчика на конкретные задачи.

Самый слепой — A. Строить ЮKасса поверх дырявой базы = юридическая ответственность при утечке платёжных данных.

Что пропустили все: Сергей соло, не технарь — реальный первый шаг — нанять/найти технического партнёра на 8–10 часов. Без этого ни один из вариантов A–D он не реализует сам.
Рецензент 3 — Сильнейший: D (Executor), Слепое пятно: C (Outsider)
Сильнейший — D. Конкретные шаги с временными оценками. Практически применимо.

Главный слепой угол — C (Outsider). «D важнее безопасности» — логика перфекционизма, не стартапа. Ручной деплой неудобен, но не блокирует продажи. Открытый RLS с клиентами — юридический и репутационный риск.

Что пропустили все: что конкретно мешает следующей продаже прямо сейчас? Может онбординг — это 10-минутный Telegram-разговор, который нужно задокументировать, не автоматизировать?
Рецензент 4 — Сильнейший: D (Executor), Слепое пятно: A (Expansionist)
Сильнейший — D. Единственный с приоритизацией C→D→B→A и временными оценками. Не просто мнение — рабочий план.

Наибольший слепой угол — A. Не ответил на вопрос. Уклонение. Говорит о «базе гостей», но вопрос про одно первое действие для автономной работы.

Что пропустили все: есть ли уже живые клиенты? Если нет — при нулевых клиентах правильный ответ B (онбординг), потому что именно он убирает Сергея из петли продаж.
Рецензент 5 — Сильнейший: B (Contrarian), Слепое пятно: A (Expansionist)
Сильнейший — B. Единственный, кто чётко обосновал приоритет: без закрытого RLS продукт нельзя подключить ни к одному клиенту. В HoReCa это мгновенная репутационная смерть.

Главный слепой — A. Нельзя брать деньги через продукт с дырами безопасности — это не только репутационный, но и юридический риск. «Первый рубль» поверх открытого RLS = первый иск.

Что пропустили все: работает ли бот прямо сейчас у первых клиентов? Что именно останавливает первую продажу завтра утром?
